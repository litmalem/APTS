# Stage 3.1.1 — Canonical Mission Identity & Envelope

This patch creates the **new Global Mission Orchestrator boundary**. It does **not** turn
VulnDesk/CTI-A01 into the global orchestrator and it does **not** move governance authority out
of aptsGSS.

## What is implemented

- authoritative global `mission_id` generated by `APTS-MO01`;
- immutable, versioned `envelope_id` + `envelope_version`;
- explicit mission provenance and client aliases;
- `correlation_id` and optional `parent_mission_id`;
- scope/RoE, PIP and governance **references** only (no authorization is performed here);
- canonical JSON + SHA-256 integrity binding;
- durable persistence (SQLite local / MariaDB-MySQL integration);
- strict create-contract validation;
- exactly-once create semantics through `(source_system, idempotency_key)`;
- HTTP API and focused acceptance tests;
- no task dispatch and no target actuation.

## Why the global identity is generated here

Before Stage 3, CTI missions could be created directly in VulnDesk with caller-supplied
`mission_id`. Stage 3 introduces a single authoritative global mission identity. Downstream CTI,
Governance, and later Pentest subsystem contracts must reuse this same `mission_id`; they must not
create competing global identities.

`client_mission_ref` exists only for correlation with pre-Stage-3/external identifiers.

## API

- `GET /health`
- `POST /api/missions`
- `GET /api/missions/{mission_id}`
- `GET /api/missions/{mission_id}/envelope`

### Minimal create request

```json
{
  "idempotency_key": "operator-20260902-001",
  "source_system": "OPERATOR_API",
  "created_by": "operator",
  "mission_kind": "AUTONOMOUS_PENTEST",
  "objective": {
    "type": "SECURITY_VALIDATION",
    "target_ref": "lab-target-01"
  },
  "scope_contract_id": "scope-...",
  "scope_version": 1,
  "policy_version": "1",
  "required_subsystems": ["CTI", "PENTEST"]
}
```

The first request returns HTTP 201. An identical retry returns HTTP 200 with
`idempotent_replay=true` and exactly the same `mission_id`, `envelope_id`, and hash. Reusing the
same idempotency key for a different canonical request returns HTTP 409.

## Local start (SQLite)

```powershell
cd D:\mission_orchestrator
python -m pip install -r .\requirements.txt
python .\run\run_mission_orchestrator.py --host 127.0.0.1 --port 8780
```

SQLite is intentionally the zero-configuration local mode. The file is created under
`data\mission_orchestrator.db`.

## MariaDB/MySQL mode

First apply:

```powershell
mysql -u root -p < .\migrations\001_stage3_1_1_canonical_mission_identity_envelope.sql
```

Then start another PowerShell:

```powershell
$env:MISSION_DB_DRIVER = "mysql"
$env:MISSION_DB_HOST = "127.0.0.1"
$env:MISSION_DB_PORT = "3306"
$env:MISSION_DB_USER = "root"
$env:MISSION_DB_PASSWORD = "<password>"
$env:MISSION_DB_NAME = "apts_mission_orchestrator"
python .\run\run_mission_orchestrator.py --host 127.0.0.1 --port 8780
```

```powershell
cd D:\mission_orchestrator
Set-ExecutionPolicy -Scope Process Bypass -Force
.\STAGE3_1_1_ACCEPTANCE.ps1
```

Expected terminal line:

```text
STAGE 3.1.1 ACCEPTANCE: PASS
```

## Intentional Stage-3.1.1 boundary

This patch does **not** implement:

- mission lifecycle/state transitions;
- planning/replanning;
- task contracts;
- CTI/Pentest dispatch;
- Governance policy evaluation;
- approval gates;
- kill-switch logic;
- event-outbox delivery;
- execution or target actuation.

Those capabilities belong to later Stage-3 sub-stages. Keeping them out of 3.1.1 makes the
identity root small, deterministic, auditable, and safe to build upon.

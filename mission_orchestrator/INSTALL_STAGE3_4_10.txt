Important
---------
Stage 3.4.10 is a closure/acceptance gate only. It must not add route-selection,
Governance, delegation, ownership-transfer, dispatch, execution, or target-actuation
authority.

Installation
------------
1. Stop the Mission Orchestrator process listening on port 8780.

2. Back up D:\mission_orchestrator and the Mission repository database.

3. Extract the Stage-3.4.10 package over D:\mission_orchestrator, preserving the
   directory structure.

4. Verify these new files exist:

   mission_orchestrator\routing_delegation_acceptance_gate.py
   tests\test_stage3_4_10_routing_delegation_acceptance_regression_gate.py
   README_STAGE3_4_10.md
   PATCH_NOTES_STAGE3_4_10.md
   PATCH_MANIFEST_STAGE3_4_10.txt
   STAGE3_4_10_ACCEPTANCE.ps1
   SHA256_STAGE3_4_10.txt

5. Database migration:

   NO NEW MIGRATION IS REQUIRED FOR STAGE 3.4.10.

   The repository must remain at migration level 26. Do not create or apply a
   migration 027 for this closure gate.

6. From PowerShell, perform source-level preflight:

   cd D:\mission_orchestrator
   python -m compileall -q mission_orchestrator tests
   python -m pytest -q tests\test_stage3_4_10_routing_delegation_acceptance_regression_gate.py

   Expected focused result:

   12 passed

7. Start/restart Mission Orchestrator using the normal project launcher.

8. Verify runtime activation:

   Invoke-RestMethod http://127.0.0.1:8780/health | ConvertTo-Json -Depth 10

     false

     true

   stage3_4_routing_delegation_acceptance_gate_new_database_migration_added
     false

Rollback
--------
Application rollback requires restoring the pre-Stage-3.4.10 source tree as one
consistent unit. Stage 3.4.10 introduces no database migration, so the repository
schema remains at level 26. Preserve the database backup anyway because acceptance
runs may create normal Mission test data if operators invoke additional live probes.
